# RW Site Review Tasks

WordPress plugin that auto-creates a recurring website-review task per company, assigned to a
maker, with a checklist, an automated site scan, a front-end maker dashboard, and a branded PDF
report. Depends on **Advanced Custom Fields PRO** (field groups are registered in code).

## Conventions

- **Function/option/hook prefix:** `srt_` — **post-type prefix:** `rwsrt_` — **text domain:** `rw-site-review-tasks`.
- **Constants:** `SRT_PLUGIN_FILE`, `SRT_PLUGIN_DIR`, `SRT_PLUGIN_URL` (defined in the main file).
- Match WordPress coding style (tabs for indentation, Yoda-free is fine, escape on output).
- **No build step.** PHP only. Lint with `php -l <file>` after edits.

## Layout

- `rw-site-review-tasks.php` — bootstrap: defines constants, `require_once`s every class, ACF-missing notice, activation/deactivation (cron schedule).
- `includes/`
  - `class-cpt-company.php` — `rwsrt_company` CPT + admin columns + **"Create review task now"** button (per-company manual run via `admin-post.php`, nonced link — never a nested `<form>`, since the meta box lives inside the post edit form). Also owns the **Checklist Items** meta box (`add_checklist_meta_box()` / `render_checklist_meta_box()` / `save_checklist()`) — a plain, non-ACF Section+Label editor with an "Add Item" button, that seeds `srt_default_checklist_items()` onto a company the first time it's saved with no checklist stored at all (covers both a brand-new company in wp-admin, whose render already pre-fills the defaults, and one created without the meta box's own nonce present at all, e.g. the CSV importer).
  - `class-cpt-task.php` — `rwsrt_task` CPT (+ admin columns). `show_in_menu` is false; tasks are reached from the company's Review Tasks meta box. Also owns the **Checklist** meta box — Section/Label are read-only reference text (the locked snapshot from the company at creation), only Answer is an editable textarea, saved via `save_checklist()`.
  - `class-acf-fields.php` — all ACF field groups + shared helpers (`srt_get_task_tag*`, `srt_user_can_access_task`, `srt_editor_post_type_capabilities`, `srt_get_assigned_user_id`, `srt_format_people_line`, `srt_default_executive_summary`, `srt_default_checklist_items`), plus the checklist storage helpers described under Data model below (`srt_get_checklist`, `srt_update_checklist`, `srt_migrate_checklist_data`).
  - `class-cron.php` — daily check (`run_daily_check`) + per-company runner (`run_for_company`), task creation/snapshot, due-date advance, maker/completion emails, Run log (retention configurable). `run_daily_check` staggers each created task's site-scan schedule by `SCAN_STAGGER_SECONDS` (120s) per company so a batch of same-day-due companies doesn't queue all their scans for the same instant; the "Create review task now" single-company path (`run_for_company` called directly) keeps the flat 60s default since there's no batch to collide with.
  - `class-site-scanner.php` — per-task site scan: broken links only (see below — WAVE, W3C validation, and PageSpeed were removed).
  - `class-mailer.php` — `SRT_Mailer::send()`, the only place notification email is built/sent. HTML body + plain-text `AltBody`, configurable From/Reply-To, envelope sender aligned with From.
  - `class-admin-settings.php` — Settings page (dashboard/task page IDs, restrict-to-maker, cron time, Run log retention, email From name/address + Reply-To, webhook URL/secret, Kinsta/GTmetrix API keys) + Run status + Run log. The former "Email deliverability" and "Integrations" explainer sections (with their test-send buttons) were removed — the underlying settings fields and `SRT_Mailer`/`SRT_Webhook` test methods they called are gone too.
  - `class-import.php` — CSV company importer. No longer sets a checklist column — new companies get the default checklist sections via the same fallback in `SRT_CPT_Company::save_checklist()` that handles any save with no checklist meta box nonce present.
  - `class-roles.php` — the optional `srt_marketing_guide` ("Marketing Guide") role, `read` only. Installed on activation and via a version-guarded `init` check (`srt_roles_version`).
  - `class-maker-dashboard.php` — `[srt_maker_dashboard]` shortcode; buckets each company's latest task into Save Draft / Upcoming / Completed. Lists companies the user is maker **or** marketing guide of. Only the latest task per company appears — there is no historical list.
  - `class-task-frontend.php` — `[srt_task_view]` shortcode; the maker's editable task form. Sections in order: Site Scan Results (+ Re-scan now) → Kinsta Data (Security Overview/Backups, each with a Refresh link and a notes textarea — Bot Protection is intentionally not shown here, it's an admin-only manual entry, MG-PDF-only) → Page Load Speed/GTmetrix (+ Refresh) → Executive Summary → checklist → Extra Notes for MG → Status (labeled Completed / Save Draft — "Save Draft" stores the same `needs_work` value as before, just relabeled). This is the same content the admin meta boxes show — since makers/marketing guides are ordinarily Subscribers with no wp-admin access to tasks at all, this page is their only view of it.
  - `class-task-print.php` — the branded PDF/print view (standard + MG variants).
- `assets/` — `dashboard.css`, `rosewood-logo.png`.

## Data model

- A **company** has a website URL, maker, marketing guide, its own **checklist**, an Executive Summary default, a review interval, next due date, a due-date rule, and lead days.
- **Checklist storage is a plain post meta array, not an ACF field at all — `srt_checklist` in `class-acf-fields.php`.** Each row is a plain associative array: `{ section, label, answer }`. Read with `srt_get_checklist( $post_id )`, write with `srt_update_checklist( $post_id, $rows )` — the latter normalizes every row to exactly those three keys, so nothing downstream ever has to guess at the shape or defend against a missing key. Used for both a company's template checklist and a task's own per-review snapshot.
  - **Why not ACF's repeater** (used through v0.3.x): a repeater stores each row's cells as their own separate `wp_postmeta` rows — a 5-row, 5-column repeater is dozens of individual database writes per save. That many-small-writes shape was the root cause of a real, observed bug where a single cell's value (the `answer` column, specifically) silently failed to persist while the rest of the row saved fine, even though `update_field()` reported success. Storing the whole checklist as one PHP array under one meta key makes a save a single atomic write, which removes that entire failure mode structurally rather than papering over it.
  - **No more `field_type`/`choices`.** The old repeater had radio/checkbox/textarea/gallery item types (`Security Overview` Plugins/Theme/Core/PHP as radios, `Page Load Speed`/Backup Verification similarly) auto-filled from Kinsta/GTmetrix. Those radio/gallery item types are gone outright — every checklist item is now just a free-text Answer (a plain `<textarea>`), and the Kinsta/GTmetrix data they used to auto-fill now shows independently in the "Kinsta Data" / "Page Load Speed (GTmetrix)" sections on the task page and both PDFs regardless of the checklist (see `class-kinsta.php` / `class-gtmetrix.php`) — those sections no longer touch the checklist at all. `srt_default_checklist_items()` keeps one free-text Summary item per affected section (Security Overview Summary, Performance and Speed Optimization Summary, Backups Summary) for the maker's own notes.
  - **Migration**: `srt_migrate_checklist_data()` (on `admin_init`, guarded by the `srt_checklist_migrated` option so it only runs once site-wide) walks every company/task post and, for any post that doesn't already have `srt_checklist` set, reads the **old** repeater's raw postmeta directly (`checklist` count + `checklist_{i}_{subfield}` cells — not `get_field()`, so it works regardless of whether the old ACF field definition is still registered) and writes it into the new `srt_checklist` key via `srt_update_checklist()`. Old `field_type`/`choices` values are dropped; Section, Label, and Answer (including old radio/checkbox answers, kept as plain text) are preserved, so no historical data is lost.
  - **Admin UI is fully custom, not ACF** — `SRT_CPT_Company`'s "Checklist Items" meta box (Section + Label inputs, add/remove rows via plain JS, no dependencies) and `SRT_CPT_Task`'s "Checklist" meta box (Section/Label shown read-only, Answer editable) each have their own nonce and `save_post_{post_type}` handler. This sidesteps the whole class of "readonly field won't submit" bugs the old ACF-repeater setup was prone to, since Section/Label on a task were never meant to be edited there in the first place.
- **Executive Summary** moved from a single hardcoded PHP default (`srt_default_executive_summary()`) applied to every task, to a company-level field seeded with that same default text but editable per company. `create_task()` now copies the *company's current* Executive Summary onto each new task, falling back to the hardcoded default only if the company's field is somehow empty.
- **Due Date Rule** (`due_date_mode`): `fixed_date` keeps the calendar day when advancing by the interval; `weekday` re-resolves `due_week` + `due_weekday` in the target month, so "last Wednesday" stays the last Wednesday instead of drifting. Helpers live in `class-acf-fields.php` (`srt_company_advance_due_date`, `srt_company_apply_due_rule`); saving a company snaps Next Due Date to the rule via `SRT_CPT_Company::snap_due_date_to_rule`.
- On schedule (or manual run), a **task** is created for a company: it **snapshots** the company's current checklist items (`section`, `label`, each with a blank `answer`) and Executive Summary at that moment via `srt_update_checklist( $task_id, $rows )`. Editing the company's checklist or Executive Summary afterward only affects tasks created from then on — each task keeps its own copy, which is what makes comparing a company's site across multiple past runs possible.
- **Snapshot self-check**: `SRT_Cron::create_task()` calls `verify_checklist_snapshot( $task_id, $expected_rows )` immediately after the snapshot write, which re-reads the checklist and, if its row count doesn't match what was just written, writes it again once; a second failure is logged (`error_log`, not silently swallowed) rather than retried indefinitely. This is now mostly a belt-and-suspenders check — with a single atomic array write there's no longer a many-small-writes race to guard against, but it costs nothing to keep.
- **Checklist sections:** a row's `section` groups it under a heading. Grouping is **sequential** — a non-empty `section` starts a group; blank-section rows continue the current group (so a section's items and its free-text summary stay together in document order). Both the PDF (`group_rows_by_section`) and the edit form use this rule.
- **Task tag** (`srt_get_task_tag_slug`): `completed`/`needs_work` come from the manual Status field; otherwise `overdue` if Period is in the past, else `ready` (an empty Period → `ready`).

## Access control

- **Admin screens are Editor-and-above.** Both CPTs (Company, Task) register with `map_meta_cap => true` and `'capabilities' => srt_editor_post_type_capabilities()`, which pins every primitive capability to `edit_others_posts` — the lowest cap an Editor has and an Author/Contributor does not. Settings and Import CSV stay on `manage_options`. The planned new admin page listing task results (filterable/exportable — see below) will follow the same `manage_options`-or-Editor pattern; nothing here changes the plugin's existing "keep it private" posture.
- **Never put `edit_post` / `read_post` / `delete_post` in that capabilities array.** `register_post_type()` passes them to `_post_type_meta_capabilities()`, which registers `$post_type_meta_caps[ <your value> ] = <meta cap>` **globally**. Aliasing them to a real primitive (e.g. `'edit_post' => 'edit_others_posts'`) makes `map_meta_cap()` reroute every site-wide `current_user_can( 'edit_others_posts' )` — core's Posts and Pages screens included — into a post-specific check with no post ID, which returns `do_not_allow`. The symptom is the plugin's admin menus silently vanishing for administrators. Only primitive caps belong in the array.
- **Front end is assignment-based, not role-based**, so a maker or marketing guide of any role (they're typically Subscribers, or hold the `srt_marketing_guide` role) can use `[srt_maker_dashboard]` and `[srt_task_view]`. `srt_user_can_access_task()` allows: anyone covered by `srt_user_can_see_all_tasks()`, whoever is named on the task, and whoever is named on the **task's company**. That last fall-through is load-bearing — see below.
- **Task assignments are snapshots; company assignments are current.** `create_task()` copies maker and marketing guide off the company at creation, so tasks created before someone was assigned carry no marketing guide, and reassigning a company leaves its existing tasks naming the previous person. Access therefore falls through to the company, which also keeps the dashboard honest: that query is company-level, so a task-only check would list a company whose task the user is then denied.
- **The Marketing Guide role (`class-roles.php`) is optional and grants nothing.** It holds `read` and nothing else; it exists so a marketing guide can have a login with no authority over the rest of the site. Their access to review work comes entirely from the ACF assignment, so an existing Subscriber works just as well. It is not removed on deactivation — that would strand assigned users.
- Both maker and marketing guide get the **same** rights on a task, including edit. If marketing guides should be read-only, that's a separate change in `class-task-frontend.php`.
- **Authenticate before checking the post type** in `class-task-print.php` and `class-task-frontend.php`, otherwise the differing responses let anonymous visitors enumerate which post IDs are review tasks.
- Read ACF user fields with `srt_get_assigned_user_id()`, never `(int) get_field(...)` — `(int) array( 5 )` is `1`, which would lock out the real assignee and match user ID 1 instead.

## Outbound HTTP (`class-site-scanner.php`)

- Links harvested from a scanned page are **third-party input** (client sites carry comments and other UGC). The page fetch and the per-link `HEAD` use `wp_safe_remote_get` / `wp_safe_remote_request`, and each link passes `is_unsafe_target()` first — that runs `wp_http_validate_url()` (blocks loopback/RFC1918 with DNS resolution, limits ports to 80/443/8080) plus a `169.254.0.0/16` check core omits, where cloud instance metadata lives.
- Blocked links are counted into `skipped` and reported in the summary — they're never listed as "broken", which would be a false finding about the client's site.

## Notification email (`class-mailer.php`)

- **Never call `wp_mail()` directly** for notifications — go through `SRT_Mailer::send( $to, $subject, $heading, $paragraphs, $cta_url, $cta_label )` so every message gets the same From/Reply-To, HTML + plain-text parts, and aligned envelope sender.
- Two notifications, both in `class-cron.php`: `notify_maker()` (task created) and `notify_status_change()` (status saved as Completed **or** Save Draft → maker + marketing guide, sent individually; wording branches on `$status` but the mechanics are identical for both). "Save Draft" is a label-only rename of the second status — the stored value, tag slug, and webhook payload are still `needs_work` (see `srt_get_task_tag_label()`); only what's shown to users changed, same as the earlier Extra Notes → Extra Notes for MG rename.
- **Deliverability split:** the plugin controls the From address, the multipart body, and Return-Path alignment. It cannot control the transport or DNS — authenticated SMTP (Kinsta does not deliver PHP `mail()`) plus SPF/DKIM/DMARC on the sending domain are required, and the Settings page says so.
- `is_from_aligned()` warns on the settings screen when the From domain isn't the site domain or a subdomain of it (relaxed DMARC alignment).

## PDF report (`class-task-print.php`)

- Styled after Rosewood's "Website Health & Security Report" (maroon title, gold section headings, serif body, cream footer with logo). CSS is inline in the print `<head>` (it does **not** load `dashboard.css`).
- Sections in order: Executive Summary → checklist groups → Kinsta Data (Security Overview / Backups / notes, plus — MG only — Bot Protection / its notes) → Page Load Speed (GTmetrix) → (MG only) Site Scan Results → (MG only) Extra Notes for MG. Kinsta Data and Page Load Speed are shown on **both** PDF variants — see `class-kinsta.php` / `class-gtmetrix.php` above; each is hidden entirely (no heading) when there's nothing to show.
- **Two variants:** standard (`srt_print_task`) and Marketing-Guide (`srt_print_task_mg`). Extra Notes for MG, Site Scan Results, Bot Protection (and its notes) are MG-only; Kinsta Data's Security Overview/Backups and Page Load Speed are not. The `extra_notes` field/meta key itself didn't change — only its label did, so no data migration was needed.
- **Unanswered checklist items are hidden entirely**, not shown with a placeholder — `row_has_answer()` filters each group before rendering, and a group left with zero visible rows after that is skipped too (no heading with nothing under it). This applies to both PDF variants.
- Site Scan Results on the MG report render **collapsed** (`render_results_html($scan, true)`) — folded `<details>`; a browser-saved PDF shows only the summary bars.
- Download filename comes from `<title>`: `{Period|today}-{Company-Name}-Website-Health-Security-Report`.
- **Page-break plumbing — don't "simplify" the `<table class="rw-flow">` wrapper away.** It exists because a `position: fixed` footer repeats on every printed page but reserves **no** space in the flow, so content ran underneath the footer band at every page break. Chrome also clips fixed elements to the page area, so the footer cannot be pushed into an `@page` margin (verified: a negative `bottom` simply doesn't paint). The two jobs are therefore split: the invisible `<tfoot>` spacer **reserves** the band on every page (table footers repeat per page fragment *and* occupy flow space), while `.rw-footer` **paints** it — a real `<tfoot>` would float up under the content on the final page instead of sitting at the bottom. `.rw-flow-spacer`'s height must stay in sync with `.rw-footer`'s.
- `@page { margin: 0.55in 0 0 }` supplies the top margin every page gets, so continuation pages don't start against the sheet edge; `.rw-page`'s `padding-top` is only page one's extra offset (the two sum to the original 0.9in). Sides and bottom stay at 0 to keep the footer band full-bleed.
- **The footer page number is hardcoded `1`** and therefore wrong on multi-page reports. Real numbering needs `counter(page)` in an `@page` margin box, which Chrome doesn't support.

## Site scan — what gets scanned, and where (`class-site-scanner.php`)

As of this rework, the scanner does **broken-link checking only**. WAVE accessibility, W3C HTML validation, and Google PageSpeed Insights were all removed (their settings fields, `check_*()` methods, and `render_*()` sections are gone from `class-site-scanner.php` and `class-admin-settings.php`) — page speed is being replaced by GTmetrix (below; not yet built), and accessibility/HTML validation were dropped outright per product decision, not replaced.

`SRT_Site_Scanner::run( $task_id )` walks a URL list — the company's homepage plus up to 5 manually added `scan_pages` (6 URLs max) — and for each page, HEAD-checks up to 60 harvested links (skipping unsafe targets — loopback/private/link-local ranges — via `is_unsafe_target()`).

Results are stored as one array in post meta (`SRT_Site_Scanner::META_KEY`) and rendered by `render_results_html()` in three places: the admin meta box (`render_admin_meta_box()`), the front-end task page (`class-task-frontend.php`, folded by default), and the MG-only section of the PDF (`class-task-print.php`, always forced collapsed).

A scan is kicked off from three places: automatically ~60s (or staggered further out in a same-day batch — see `class-cron.php`) after a task is created by the daily check or "Create review task now"; or manually and immediately via "Re-scan now" (`rescan_url()`) in either the admin meta box or the front-end task page (`handle_rescan()` → `run()` directly, no delay). The front-end link passes its own URL as a return target (see `srt_redirect_after_action()` in `class-acf-fields.php`) so a maker lands back on the task page, not a wp-admin screen they likely can't open.

## Kinsta integration (`class-kinsta.php`)

Pulls Security Overview data and the Backups date from the Kinsta REST API, both tied to a task and refreshable independently of the company's Due Date Rule/schedule. Endpoint shapes below were confirmed directly against Kinsta's published OpenAPI spec (`api-docs.kinsta.com`), not guessed.

- **Setup**: `srt_kinsta_api_key` (Settings) is the account-wide Bearer token. Each company additionally needs its own `kinsta_site_id` (the site's UUID in MyKinsta) — without it, Kinsta data is skipped for that company's tasks, same inert-until-configured pattern as the webhook.
- **Auth & base URL**: `Authorization: Bearer <key>`, `https://api.kinsta.com/v2`.
- **Resolving a site to an environment**: there's no "get one environment" endpoint — only `GET /sites/{site_id}/environments`, which lists every environment (live, staging, …) for that site. `resolve_live_environment()` calls this and picks the one named `live` (falling back to the first if none is), since that's the environment the env-scoped endpoints below need an ID for.
- **Security Overview** (`fetch_security()`): `GET /sites/environments/{env_id}/wp-plugins` and `.../wp-themes` (each item carries `update: "available"` or not — counted client-side for "N updates available"); `wordpress_version` and `container_info.php_engine_version` come off the resolved environment object. Core is compared against the actual latest WordPress release (the free, keyless `api.wordpress.org/core/version-check/1.7/`); PHP is compared against `srt_kinsta_recommended_php` (Settings, default `8.3` — bump this as the recommended baseline changes).
- **No checklist auto-fill.** Earlier versions had `apply_security_to_checklist()` matching Security Overview's four `radio`-type checklist items (Plugins/Theme/Core/PHP Version) by label and setting their answer from the fetched status. That method (and the old radio-type items it targeted) is gone — the checklist is textarea-only now, and this data is rendered independently of it (below), so there's nothing left to auto-fill.
- **Backups** (`fetch_backups()`): `GET /sites/environments/{env_id}/backups` → most recent `created_at` (epoch ms) across all returned backups.
- **Bot Protection is not automated, and is admin/MG-only.** Kinsta's public REST API (checked directly against their endpoint index while building this) has no Bot Protection / traffic-analytics endpoint at all as of this writing — the feature is too new. Instead there's a manual-entry fallback: three number fields (Allowed/Challenged/Blocked) on the task's "Kinsta Data" admin meta box, saved via `handle_save_bot_protection()`. Rendered by `render_bot_protection_html()` **only on the MG PDF** — it's deliberately not shown on the front-end task page at all (makers/marketing guides can't enter the numbers there anyway, so showing a read-only, always-empty-looking block was more confusing than useful).
- **Rendering is independent of the checklist.** Earlier, Security Overview/Backups only appeared beside a checklist item with a matching label — so a task with no checklist items (or one that didn't include those labels) showed none of this data, on either PDF. `render_security_overview_html()` and `render_backups_html()` are now public, take an optional pre-fetched array (`$security`/`$backups`) to avoid a redundant `get_results()` call, and return `''` when there's nothing ready to show — callers (admin meta box, front-end task page, both PDFs) use that to skip the section/subsection entirely rather than print an empty one.
- **Notes fields**: three plain ACF textareas on the task — `kinsta_security_notes`, `kinsta_backups_notes`, `kinsta_bot_protection_notes`. The first two are editable on the front-end task page below their subsection; `kinsta_bot_protection_notes` is wp-admin-only (edited via the standard ACF "Task Details" box there, since the whole Bot Protection block is admin/MG-only). All three are shown on both PDFs directly under their matching subsection (Bot Protection's notes MG-only, like the block itself) and hidden entirely (no empty paragraph) when blank.
- **Scheduling & refresh**: `SRT_Kinsta::schedule()` fires alongside `SRT_Site_Scanner::schedule()` in `SRT_Cron::create_task()` (same delay/stagger). Both the admin meta box and the front-end task page's "Kinsta Data" section have "Refresh Security Overview" / "Refresh Backups" links (`security_refresh_url()` / `backups_refresh_url()`, `admin-post.php`, nonced) that re-fetch just that one piece and re-save just that piece of `SRT_Kinsta::META_KEY` — neither touches the company's due date.
- **Front-end access**: makers and marketing guides are ordinarily Subscribers with no `edit_post` capability, so `current_user_can( 'edit_post', $task_id )` — the check these admin-post handlers originally used — denied them even though the front-end task page is *their* editing surface. The refresh/rescan handlers (here, in `class-gtmetrix.php`, and in `class-site-scanner.php`) now accept either that capability *or* `srt_user_can_access_task()` via the shared `srt_user_can_manage_task()` helper (`class-acf-fields.php`), and redirect back to whichever page the link was clicked from via `srt_redirect_after_action()` (an `srt_return` query arg carries the front-end task page URL; omitted, it falls back to the wp-admin edit screen as before) — so a maker clicking "Refresh" on the task page lands back on the task page, not a wp-admin 403.

## GTmetrix integration (`class-gtmetrix.php`)

Replaces PageSpeed Insights entirely. Runs a real GTmetrix test per task on its scheduled date and shows the current run next to the previous one for comparison. Endpoint shapes below were confirmed directly against GTmetrix's published API v2.0 docs (`gtmetrix.com/api/docs/2.0/`), not guessed.

- **Setup**: `srt_gtmetrix_api_key` (Settings → Pages & Access) is the account-wide API key; it's inert until set.
- **Multi-page**: tests every page in the company's scan list — homepage (`website_url`) plus up to 5 "Additional Pages to Scan" (`scan_pages`, the same field `class-site-scanner.php` reads), homepage-plus-5/6-max, same as the broken-link scanner. Each page runs and is tracked as its own fully independent GTmetrix test/poll cycle — one page erroring or timing out never blocks the others — under `$results['pages'][index] = { url, status, test_id, current, previous, error }` (`status`: `''`|`pending`|`error`|`ready`). Because this multiplies the account's daily GTmetrix test allowance by the number of pages scanned, free-tier accounts should watch their usage if several companies have Additional Pages configured.
- **Auth & base URL**: HTTP Basic auth with the API key as the username and a blank password (`Authorization: Basic base64(key + ':')`), `https://gtmetrix.com/api/2.0`.
- **Async start/poll flow**: GTmetrix tests aren't instant, so this mirrors the schedule-then-fetch shape the site scan and Kinsta pull already use, but with an extra polling leg since GTmetrix's job can take longer than one WP-Cron pass:
  - `SRT_GTmetrix::schedule( $task_id, $delay )` fires alongside `SRT_Site_Scanner::schedule()` / `SRT_Kinsta::schedule()` in `SRT_Cron::create_task()` (same delay/stagger), scheduling `start_test()` on the `srt_gtmetrix_start` hook.
  - `start_test()` builds the page list and loops it, calling `start_page_test()` for each — one `POST /tests` per page/URL — storing each page's test id and scheduling its own `poll_test( $task_id, $page_index, 1 )` on `srt_gtmetrix_poll` roughly `POLL_INTERVAL` (15s) later.
  - `poll_test()` does `GET /tests/{id}` for that page's test. WordPress's HTTP API auto-follows the 303 redirect GTmetrix returns on completion, so a "completed" response already contains the full report in the same call — no separate report fetch needed. If the state is still `queued`/`started`, it re-schedules itself for that page only, capped at `MAX_POLL_ATTEMPTS` (20 tries per page).
  - On completion, `apply_page_report()` reads `gtmetrix_grade`, `performance_score`, `structure_score`, `largest_contentful_paint`, `total_blocking_time`, and `cumulative_layout_shift` off the report, rotates that page's previous `current` into `previous` (so exactly one prior run per page is always kept for comparison), and saves it into that page's entry under `SRT_GTmetrix::META_KEY`.
- **No checklist auto-fill.** Earlier versions had `apply_to_checklist()` (homepage-only) matching a `radio`-type "Page Load Speed" checklist item by label and setting its answer from the computed performance grade. That method (and the old radio-type item it targeted) is gone — the per-page comparison tables below are the only place this data shows, independent of the checklist entirely.
- **Rendering**: `render_table_html( $results, $task_id, $ready_only )` renders one block per page (Homepage/Page heading + URL), each showing its own not-tested/pending/error state or a vertical Previous/Current comparison table (Grade, Performance, Structure, LCP, TBT, CLS, each column labeled with its test date). Shown as the "Page Load Speed (GTmetrix)" section — not tied to a checklist item — on the front-end task page (`class-task-frontend.php`) and both PDFs (`class-task-print.php`). The front-end/admin meta box show every page's state (including pending/error); the PDFs pass `$ready_only = true` so only completed pages appear, same as before, and the whole section is hidden when nothing is ready yet.
- **Refresh**: `refresh_url()` (public) builds the nonced link; both the "Page Load Speed (GTmetrix)" admin meta box and the front-end task page's section use it (`class-gtmetrix.php`, `admin-post.php`, `SRT_GTmetrix::REFRESH_ACTION`) to kick off a fresh `start_test()` (all pages) on demand, without touching the company's due date. Front-end access uses the same `srt_user_can_manage_task()` / `srt_redirect_after_action()` pattern described under Kinsta above.

## Task Results admin page (`class-results-admin.php`)

A private admin page (Companies → Task Results, `manage_options` only, same access level as every other admin screen here) listing every review task across every company in one table.

- **Filters**: Company (dropdown of all companies), Status (Completed / Save Draft / Overdue / Ready / all), and a Period date range (from/to). Completed and Save Draft are real `status` meta values (`completed` / `needs_work`) and filter via `meta_query`; Overdue and Ready are derived (empty `status` + Period vs today, via the existing `srt_get_task_tag_slug()`), so those two are filtered in PHP after the date-ranged `meta_query` fetch rather than in the query itself.
- **Table columns**: Company, Period, Status (colored badge, now linking to that task's front-end page via `srt_task_page_url()` — opens in a new tab, falls back to plain text if no Task Detail page is configured in Settings), Maker, Marketing Guide, Created, Core/Plugins/Theme/PHP (one column each, from `SRT_Kinsta::get_results()['security']` — shows the actual version/update-count `detail` text, e.g. "WordPress 6.4" or "3 updates available (...)", colored green/red by `status`; `—` if there's no data yet), Last Backup (`['backups']['last_backup']`), Page1–Page6 (one column per scan slot — homepage plus up to 5 Additional Pages to Scan, from `SRT_GTmetrix::get_results()['pages']`; a slot shows the current performance score, or Pending/Error/— while that page hasn't completed a run, and is left **blank** if the company has no page configured at that slot), and a link to the task.
- **CSV export**: an "Export CSV" button next to the filters hits a nonced `admin_post` action (`srt_export_results`) carrying the same filter values, so the export always matches exactly what's on screen. Columns mirror the on-screen table one-for-one: Task ID, Company, Period, Status, Maker, Marketing Guide, Created, Core, Plugins, Theme, PHP, Last Backup, Page1–Page6, Task Edit URL.
- **Note**: filters and export both key off Period (the due date the review is for) rather than the task's creation date — matches the "Due" column used elsewhere (Run log, company task list).

### Adding a new external scan check (the existing pattern)

The broken-link check that remains follows this shape: a private `check_*( $url )` method in `class-site-scanner.php` that makes one `wp_remote_get()`/`wp_remote_request()` call and returns a small result array, a call to it inside `run()`, and a `render_*_section()` method wired into `render_results_html()` to draw its `<details>` block and colored badge. Kinsta and GTmetrix don't fit this pattern as cleanly — see their own sections above.

**Screaming Frog**, if ever revisited: it's not a hosted API callable with `wp_remote_get()`, it's a licensed desktop application whose CLI/headless mode is meant to run on a machine you control — not inside a shared WordPress host like Kinsta, which won't let this plugin shell out to an external binary. Integrating it would mean standing up a separate server with Screaming Frog installed and licensed, running scheduled headless crawls there, and having that machine POST its results to a new *inbound* endpoint here — the mirror image of the outbound webhook this plugin already sends (below).

## Outbound webhook (`class-webhook.php`)

- `class-task-frontend.php` fires `do_action( 'srt_task_status_changed', $task_id, $status, $old_status )` whenever a task's status is saved as `completed` or `needs_work` and actually changed. `SRT_Webhook::handle_status_change()` is the only listener today, but any other plugin/mu-plugin can hook the same action to sync elsewhere without touching this plugin.
- Inert until `srt_webhook_url` (Settings → Pages & Access) is set. `SRT_Webhook::send()` POSTs JSON via `wp_remote_post()`; if `srt_webhook_secret` is also set, the request carries `X-SRT-Signature: hash_hmac( 'sha256', $raw_body, $secret )`.
- Payload shape (`build_payload()`): `event`, `task_id`, `status`, `status_label`, `previous_status`, `company_id`, `company_name`, `period`, `task_url`, `site`, `timestamp`.

## Gotchas

- The Review Tasks meta box renders **inside** the WordPress post `<form>`. Never emit a nested `<form>` there — use nonced links to `admin-post.php` (see the per-company run button and the re-scan link).
- The maker dashboard is **company-centric**: it shows one tile per company (the latest task), only for companies the user makes (when "Restrict to assigned maker" is on) and that are published. Tasks with no Period still show (treated as Ready).
- Checklist section/label fields must be carried through the snapshot in `SRT_Cron::create_task` — the task stores its own copy, so editing a company's checklist afterward doesn't retro-apply to existing tasks.
- **A company's checklist only gets the defaults re-seeded when it has never had `srt_checklist` set at all** (`SRT_CPT_Company::save_checklist()` checks `metadata_exists()`, not "is it currently empty"). Unlike the old ACF-repeater behavior, deliberately clearing a company's checklist down to zero rows now **stays** empty on future saves — it will not silently repopulate. This was an intentional behavior change made as part of the checklist rebuild (see Data model above).
